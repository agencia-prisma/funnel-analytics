# EPIC 10 — Funnel Progression + Conversion Facts

## Goal

Connect the two foundations introduced previously:

```text
Journey Engine
  +
Immutable Funnel Definition V1
  ↓
Funnel Progression Engine
  ↓
Step Hits + Transitions + Conversions
```

EPIC 10 is the first layer that materializes funnel analytics.

## Pipeline

```text
Session / Identity change
        ↓
Journey Worker
        ↓
funnel-analytics-funnels-<env>
        ↓
Funnel Worker
        ├─ Supabase: active immutable Funnel Versions
        ├─ ClickHouse: Journey + Journey events
        ↓
@funnel/funnel-engine
        ↓
ClickHouse funnel facts
```

The Journey Worker publishes funnel recomputation only after the Journey state has been persisted. It acknowledges the upstream message only after the downstream queue publish succeeds.

## Recompute envelope

A Funnel recompute message carries:

- Workspace ID;
- current Journey IDs;
- deleted/reconciled Journey IDs;
- source Journey version;
- generation time.

Messages contain at most 100 Journey references and are chunked by the Journey Worker.

## Control Plane

The Funnel Worker reads active funnels from Supabase using the server-side key.

For each active funnel it retrieves exactly the `current_version_id`, its immutable version metadata and ordered steps. The returned definition is validated again with `@funnel/rule-engine` before evaluation.

A malformed active definition is treated as a permanent integrity failure. The Worker does not generate analytics from structurally invalid rules.

## Progression semantics

V1 is strict and ordered.

Example:

```text
1 Landing
2 Lead
3 Checkout
4 Purchase
```

`Checkout` before `Lead` is ignored for the current attempt. The attempt progresses only when the next expected step matches.

A single event may advance no more than one step.

The conversion window begins on the first-step event. Expired attempts stay incomplete and a new first-step event can open another attempt. Multiple attempts and multiple conversions are therefore possible inside one Journey.

## ClickHouse facts

Migration `0005_funnel_facts.sql` adds three versioned datasets.

### `funnel_step_hits`

Represents reached funnel steps.

Key analytical dimensions include:

- Workspace;
- Funnel and immutable Funnel Version;
- Journey;
- deterministic attempt;
- step key and position;
- event/session/visitor/pixel;
- Person ID when resolved;
- entry time, hit time and elapsed milliseconds;
- `test_mode`.

### `funnel_transition_facts`

Represents consecutive reached-step transitions and their latency.

Example:

```text
Landing → Lead = 18,200 ms
Lead → Checkout = 94,500 ms
```

### `funnel_conversion_facts`

Represents completed funnel attempts.

Each conversion stores:

- attempt;
- entry event;
- conversion event;
- entry/conversion timestamps;
- total conversion duration;
- total number of steps.

## Versioning and reconciliation

Every analytical row carries both:

```text
funnel_version_id
source_journey_version
```

`funnel_version_id` identifies the immutable business definition that interpreted the events.

`source_journey_version` identifies the exact Journey state that supplied the events/mapping.

Fact rows use `ReplacingMergeTree` with a monotonic `fact_version` derived from the source Journey version. When a Journey is recomputed, old facts for the same Journey + Funnel Version are tombstoned before the new state is inserted.

When identity reconciliation deletes an old Journey, all current Funnel facts for that Journey are tombstoned.

Older out-of-order queue messages cannot overwrite a newer Journey-derived fact state because their fact versions are lower.

## Historical correctness

Changing a Funnel creates a new `funnel_version_id`; it does not mutate facts generated by an older definition.

Historical facts for old versions remain available. Product queries that represent the current funnel should resolve the current version from the Control Plane.

EPIC 10 does not automatically backfill all historical Journeys when a new Funnel Version is published. That is intentionally separated from the real-time recomputation path.

## Security and PII

The new ClickHouse fact tables contain analytical identifiers only. They do not store email, phone, CPF, encrypted PII, blind indexes or names.

`person_id` is the only resolved identity reference and remains a UUID.

The Funnel Worker declares all Supabase and ClickHouse runtime secrets as required Wrangler secrets, making missing bindings a deployment-time failure rather than a generic runtime network error.

## Failure behavior

Permanent failures go to the Funnel DLQ and are acknowledged:

- invalid envelope;
- invalid control-plane configuration/URL;
- malformed active Funnel Definition;
- invalid fact schema/integrity input.

Transient failures are retried:

- Supabase availability failures;
- ClickHouse query/write availability failures.

## What becomes possible after EPIC 10

The stored facts are sufficient to derive:

- unique entries per Funnel/step;
- step-to-step conversion rate;
- funnel completion rate;
- drop-off by step;
- median/average time between steps;
- median/average time to conversion;
- repeated attempts per Journey;
- conversion analysis by Journey/Person/test-mode.

## Out of scope

EPIC 10 does not yet implement:

- revenue and AOV facts;
- purchase/order normalization;
- Hotmart/Kiwify/checkout ingestion;
- attribution model facts;
- historical backfill on Funnel Version publication;
- dashboard query API;
- Funnel Builder UI.
